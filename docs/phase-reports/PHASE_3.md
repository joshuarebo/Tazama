# Phase 3 — Insights and ML

Status: **gate green**. The forecast beats its baseline on the metric that matters, the
anomaly detector meets its recall floor at a workable alert volume, and both are
registered with model cards.

The honest headline, though, is that the first version of this gate was green on a model
that had learned nothing. That took three attempts to find and is the most useful thing in
this report.

## 3. The gate that was green and wrong

Worth reading in full, because the same trap is waiting in any sparse-target problem.

**Attempt 1.** The forecast reported "model beats baseline on test_mae: 0.011305 vs
0.018910 (+40.2%)". Gate green. The number was real and the conclusion was worthless: the
target — complaints per 1,000 subscribers per *cell*-hour — is **97.6% zeros**, and the
training objective was `regression_l1`. The L1 optimum of a mostly-zero series is its
median, which is zero. So LightGBM dutifully learned to predict the constant 0.0, which
scores an excellent MAE and comfortably beats a seasonal-naive baseline that honestly
carries last week's spikes forward and is therefore wrong whenever a spike does not repeat.

The symptom that gave it away was in the report all along: every SHAP value printed as
`0.00000`. A model with 400 trees and zero attribution is a model whose output does not
depend on its input.

**The three fixes, in order of importance:**

1. **Measure the thing that cannot be won by predicting nothing.** `RegressionMetrics`
   gained `pred_std` (zero ⇒ a constant predictor) and `mae_nonzero` (error restricted to
   the hours where demand actually occurred). The gate now fails on either a degenerate
   predictor or a loss on the non-zero rows, whatever the overall MAE says.

2. **Use an objective that fits the data.** `poisson` replaced `regression_l1`. The target
   is a non-negative arrival rate, which is what Poisson deviance is for, and unlike L1 it
   cannot collapse to the median.

3. **Forecast at a granularity where the signal exists.** Measured: 97.6% zeros at
   cell-hour, **16.7% at region-hour**. This was the decisive change — no objective beat
   the baseline on the non-zero rows at cell grain. It is also the right answer on the
   merits: a call-surge forecast exists to plan care staffing, and staffing is planned per
   region. `build_feature_frame(grain="region")` aggregates before the lags are taken, so
   each lag describes the region's own history rather than averaging per-cell lags.

**Attempt 2** then failed differently and usefully: the region frame was being built from
a 60-cell subsample, so the "regional rate" was a rate over an arbitrary 10% of each
region with the denominator to match. The same model went from +18% to −3% purely because
of the subsample. `cell_limit` is now ignored at region grain, with the reason recorded in
the constant's docstring.

## 4. Other real defects found

1. **`ml_repo` read every registry row through a Core connection.** `select(MappedClass)`
   on a `Connection` returns columns, not the mapped object, so `_entry(row[0])` read
   attributes off a string. It only broke on the engine-only path — the training CLI's
   path — which is where it was least likely to be noticed. Both branches now use a
   `Session`.

2. **The leakage gate failed clean data.** `_matches` answers "is this a reproduction of
   something forbidden", where "cannot tell" must be `False`. The re-derivation check asks
   the opposite question — "is this really the shifted column it claims to be" — where
   `False` means *leak*. Reusing one helper for both meant a KPI counter that happened to
   be flat across the window read as leakage. The indeterminate case is now named once and
   both callers handle it explicitly.

3. **The anomaly detector could not see a total collapse.** A healthy availability counter
   sits pinned at 100.000, giving MAD = 0, and the code required `spread > 0` — so a drop
   to 12% divided by zero, scored `NaN`, and was silently dropped. The worst outage in the
   window was the one thing the detector could not see. Any departure from a perfectly
   constant history is unbounded evidence, so it is now scored at a large finite value with
   the sign preserved.

4. **The test fixture was too clean to be data.** With complaints an exact function of
   congestion, every KPI became perfectly rank-correlated with the target and the leakage
   gate refused the frame — correctly, since on real data a Spearman ρ of 1.0 between a
   lagged KPI and the target *is* leakage. The fixture now carries deterministic
   hash-derived noise, which keeps the reproducibility tests exact.

## 5. Deviations from the plan

| Planned | Built | Why |
| --- | --- | --- |
| Forecast per cell | Forecast per **region** | The cell-hour target is 97.6% zeros and unlearnable; measured, not assumed |
| `regression_l1` objective | `poisson` | L1 on a sparse count target trains a constant |
| Anomaly gate: precision ≥ 0.10 | Recall ≥ 0.50 **and** flag rate ≤ 5% | See §6 |
| UMAP for visualisation | Not built | Dependency not justified for a demo-sized corpus; PCA covers the structure question. Tech-debt |
| Component unit tests for insights panels | Playwright journeys + a11y suite | Phase 5; recorded as a gap |

## 6. Assumptions and judgement calls

**The anomaly precision floor was replaced by a flag-rate ceiling.** The labels are
incident windows, and an incident exists only where correlation had enough evidence to
raise one — so a genuine degradation that produced no incident counts as a false positive,
and measured precision lands near 0.005 to 0.015 however good the detector is. Gating on a
number that cannot be reached teaches a team to switch the gate off. The flag rate (3.93%
of cell-hours) answers the question that actually matters operationally — *will this drown
whoever is on shift* — and precision is still recorded on the card and in `eval_run` as a
number to watch.

**Model versions are derived from the data hash and the gate thresholds**, not the clock.
Re-running `make train` on an unchanged database is therefore idempotent rather than a
crash, and moving a threshold produces a new version instead of silently contradicting the
row already on file.

**Every metric here is optimistic.** The seed's relationships are the ones the generator
put there. A real network is noisier, less consistent, and will have relationships this
data does not contain. Each model card says so in its own limitations section.

## 7. Known gaps

1. **No GNN, no bandit.** Scaffolds exist, are flagged off, and refuse to run. They must
   beat LightGBM on the eval set first (PRD §9).
2. **The priority model is trained on synthetic labels** distilled from the existing rule,
   so it can only learn to imitate that rule. It is registered but the rule remains in
   control, and the card says why.
3. **Feedback bias.** Models are trained on data shaped by their own suppression decisions.
   An exploration slice is retained and decisions are logged with versions, but nothing
   corrects for it yet (tech-debt #11).
4. **Re-identification risk in the insights surface.** A per-cell complaint rate at 03:00
   on a twelve-subscriber cell is close to identifying. `docs/dpia.md` §7 requires a
   minimum-exposure floor before real data.
5. **The forecast horizon is one hour.** Nothing here supports a longer one, and care
   staffing decisions are often made a shift ahead.
6. **No drift monitoring in production.** PSI is implemented and tested; nothing runs it on
   a schedule.
